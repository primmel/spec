[[data-quantities-time]]
== Data, quantities, and time

[[data-classes]]
=== Data classes, enumerations, and registries

[[lutaml-surface]]
The attribute surface is LUTAML'S (<<semantic-basis,6.2>>, the
data-modeling surface of the object/property/value axis): an
attribute is `attribute <name>, <Type> { <facets> }` — the name and
the type separated by a comma, the facets in a block — with the
facets LutaML defines plus the two the SMART documentation adds to
the attribute (modality and reference):

[source,prl]
----
class LoadCellSample {
  attribute serial_number, String { definition "The manufacturer's serial number" modality SHALL }
  attribute e_max, Mass { definition "Maximum capacity" cardinality 1..1 }
  attribute accuracy_class, AccuracyClass { values AccuracyClass }
}
enum AccuracyClass {
  value "A" { definition "the special class" }
  value "B"
  value "C"
  value "D"
}
----

The facets: `definition` (LutaML), `cardinality <min>..<max>` with `*`
for unbounded (LutaML), `values` — a closed value set inline or an
`enum` reference (LutaML), `modality` (the SMART documentation: the
attribute carries requirement modality), and `reference` (the SMART
documentation: a clause citation). An attribute of an enumeration
type renders as the closed set; a quantity-valued attribute names its
unit and kind through the quantity register.

A class declares a record shape; the `#data` suffix marks a class as
registerable. A class without `#data` is a helper class: a reusable
complex type that lives as an attribute inside other classes and
cannot be registered — the SMART documentation's DATA CLASS. A class
marked `#data`, or referenced by a `data_registry`, is the
documentation's REGISTRY data structure: a structure AND the place
records are kept (<<evidence-law,6.2>>).

An `instance` states values in LUTAML'S ASSIGNMENT FORM — `attribute
= value`, one per line — with Primmel's instantiation refinements
riding their declared facets:

[source,prl]
----
instance smp-001 {
  of LoadCellSample
  serial_number = "HBK-001"
  e_max = 2.2 t
  accuracy_class = "C"
}
----

[NOTE]
--
The v2 field dialect `<name>: <type> [<cardinality>] { … }` migrates
mechanically to the LutaML form (`name: T [0..1] { … }` →
`attribute name, T { cardinality 0..1 … }`); the migration tooling
ships with the kernel (phase 2 of the full flow), and the v2 dialect
is rejected after the migration window.
--

A `data_registry` declares a named store of records of one data class
(facets `title`, `data_class`); processes read and write registries
through their `reference_data_registry` and `output` facets
(<<process-subject,12.1>>).

[[field-types]]
=== Field types

The primitive field types are `string`, `boolean`, `datetime`, and
`role`. A field type may also name an enumeration (one of its values), a
helper class (an embedded complex value), or a typed reference
`reference(<Target>#data)` (a foreign key to another registry's record).
A field with no type is free-form.

[[measurements]]
=== Measurements

A `measurement` (legacy alias `variable`) declares a value that validation
expressions and gateway conditions evaluate:

[source,prl]
----
measurement MoistureReading {
  type DATALIST
  description "Per-batch moisture readings in percent by mass"
}
measurement MaxMoisture {
  type DERIVED
  definition { [MoistureReading].max }
}
----

The documented measurement-type vocabulary (MN 113) is `NUMERIC`,
`DATALIST`, `DERIVED`, `TEXT`, `TABLE_REFERENCE`, `TRUE/FALSE`, and
`DURATION`; the type is stored as text, and the derivation definition of a
`DERIVED` measurement is the consumer's expression dialect.

A collection may carry its ELEMENT TYPE (CRITIQUE-3 #4):
`type collection<Row>` where `Row` names a declared data class — the
navigation's lambda parameter then reads against the class's attributes,
and an unknown member is air (C194,
<<checker,16>>). The parameterized form is opt-in: a bare `collection`
stays untyped, and every existing collection declaration reads exactly
as before.

[[quantities]]
=== Quantities and units

A `quantity_register` upgrades bare unit strings into typed register
entries: quantity kinds with their dimension vectors and SI coherent
units, and units with their symbols, kinds, and SI conversions.

[source,prl]
----
quantity_register si {
  kind mass { dimensions { M 1 } si_unit kg description "Mass." }
  unit kg { symbol "kg" label "kilogram" kind mass factor 1 }
  unit g { symbol "g" label "gram" kind mass factor 0.001 }
  unit degC { symbol "°C" label "degree Celsius" kind temperature factor 1 offset 273.15 }
}
----

A kind carries `dimensions { <base> <exponent> ... }` and `si_unit`; a
unit carries `symbol`, `label`, `kind`, the multiplicative `factor`, and
the affine `offset`. Comparison coherence is judged on kinds, not unit
strings (C33), and a package extends a register without redefining its
entries (C32, C33). A `series` declaration on a symbol or variable states
the axes and cell shape of a reading series.

A quantity register is self-contained: its kinds, units, factors, and
offsets are Primmel's own content. The IDENTIFIER SPELLING of a kind
or unit is the register's, verbatim: a condition-set entry key, a
quantity_kind reference, or a unit reference names the register's
declared identifier exactly — the language carries no
underscore/hyphen equivalence, and the checker (C33) treats a
spelling mismatch as incoherence. Where a document-side toolchain
carries a unit vocabulary (UnitsML is the document format's register),
the binding rides the correspondence annotation of
<<correspondence-annotations,19.4>> — a unit or kind entry declares
`corresponds unitsml "<unit-identifier>"`, a maps-to claim that steers
the document projections and never imports the register's semantics
(<<expression-layer,19.5>>).

A unit may also pin the UnitsDB release directly — `unitsdb { nist
"<id>" unitsml "<id>" }` — the machine-readable register the corpus's
stem blocks carry UnitsML markup for. The DB is authoritative for the
decomposition STRUCTURE (the si_derived_bases walk to the SI bases,
the prefixes, the measurement scale); the register keeps its authored
conversion numbers, and the checker verifies the pin against a
supplied UnitsDB snapshot (C185 unitsdb-binding-coherent) — the
interval-scale offsets (degree Celsius's 273.15) live in the register,
never in the DB. The retrieval export carries the pin's identifiers
and the resolved SI structure onto the emitted units when the export
is given the snapshot.

[[numeric-semantics]]
=== Numeric semantics

A surface numeric literal is an EXACT DECIMAL. The authored form of a
quantity value — its value, its uncertainty, its tolerance — is part of
the value: `2.10 kg` is a precision statement (two decimals —
significant figures), never a misspelling of `2.1 kg`. A quantity value
whose authored literal carries information the number alone loses
(trailing zeros, an explicit exponent form) preserves that literal
verbatim on the wire; the conforming serializer emits it unchanged, and
the round trip is the proof. Auxiliary numerics — register factors,
offsets, column defs, orders — have no precision statement to carry and
canonicalize to the number. An expression literal carries the same
precision statement: the canonicalizer replays the authored number
token verbatim — `2.10` stays `2.10`, `.5` stays `.5`, an exponent form
stays the exponent form — while the evaluator reads every accepted
spelling (integer, fraction, leading dot, exponent) as the number it
denotes. Comparisons (limits, checks, acceptance
decisions) evaluate in binary double precision (IEEE 754); the corpus's
acceptance bounds are coarse by doctrine (MPE apportioning, class
tables), never parked at a representable edge, and a scheme that needs
exact-decimal adjudication declares it in the check rather than in the
number.

[[dual-construct]]
=== The value duality: dual

A `dual` declares the IS/HAS duality (<<is-has-duality,10.4>>) of one
attribute explicitly:

[source,prl]
----
dual e-max-rating {
  attribute e_max
  designed  { value 2.2 unit t tolerance 0.5 }
  exhibited { value 2.1998 unit t uncertainty 0.0002 }
}
----

The `designed` side is the IS role (carrying `tolerance`); the
`exhibited` side is the HAS role (carrying `uncertainty`). At least one
side is present; when both are stated they must be kind-coherent (C34).

[[datum-construct]]
=== The datum

A `datum` declares one typed, unit-bearing value of the model's data
registry — the declared facts a formula, a limit, or an evaluation
reads. The datum is the duality's registry face: where `dual` relates a
quantity's two roles, the datum is the declared record a role's value
resolves against.

[source,prl]
----
datum reference_volume : number {
  label "Reference volume"
  unit "m3"
  quantity_kind volume
  origin observed
  scope type_evaluation
  description "The reference volume of the test run (3.2.1)."
  render latex "V_{\mathrm{a}}"
}
----

The facets: the type rides the head (`datum <id> : <type>`); `label`
and `description` carry the human surface (the description may be a
block); `unit` and `quantity_kind` declare the measure — a value stated
for a declared quantity carries its unit (C32); `origin` is a closed
vocabulary, parse-enforced: `declared`, `design-fixed`, `observed`,
`computed`; `scope` names the regime the datum belongs to; and each
`render` pair declares the datum's presentation in a declared math
notation. Declared datums join the checker's identifier registries: an
expression argument may bind `datum:<id>` (<<limit-expressions,11.1.4>>).

[[datum-unification]]
=== The datum unification: one substrate, four plane surfaces

The datum is the language's SUBSTRATE for "a named, typed, unit-ed
value" — one declaration shape, one set of axes. The substrate carries
the identifier and the type; the unit and the quantity kind
(<<quantities>>); the ORIGIN, the epistemic axis — where the value's
authority comes from: `declared` (the manufacturer asserts it),
`design-fixed` (invariant by construction), `observed` (measured in a
run, by whatever executor — a twin-measured reading is observed all
the same), `computed` (derived by the model's own calculations); the
SCOPE, the regime the value lives in (model, family, group, and the
evaluation and run regimes between); the renders, the `render` pairs
of <<datum-construct>>; and the typed refs
(<<provenance-forms,14.3>>).

Four plane carriers NAME this substrate, each keeping its plane's
extras — extras on a shared substrate, never competing definitions of
the value:

* `attribute_definition` (<<subject-model>>) is the MODEL plane's
carrier; its extras are the model plane's: `category`, `is_dimension`,
the `enum` binding, and the `irdi` correspondence.
* `identity_slot` (<<identity-slot-construct>>) is the INSCRIPTION
plane's carrier; its extras are the presentation surfaces (the
marking channels) and the slot's class in the scheme's marking
register.
* the capability's `has_parameters` is the COMPOSITION plane's face,
and never its own value grammar: a composition-scoped SELECTION of
declared datums, the names it lists being names the substrate already
carries.
* the form `field` (<<form-constructs>>) is the RUN plane's carrier;
its extras are the `bind` path, the `verdict` it derives, the
`required` / `required_when` gate, and the field's validation stack.

The carriers are ALIASES, not competitors: parse-level spellings of
the one substrate. A later revision retires a carrier spelling only
after its corpus migration — the deprecation ladder every spelling
change follows; until then both spellings are legal, and the checker
treats them as the same class of thing. The unification's schedule —
which carrier migrates when — is the kernel register's
(TODO.lang-gaps/04), not this clause's.

Dimension values and table columns state VALUES of declared axes;
they are not value declarations of their own. A dimension value names
the dimension and states the value; a table column types the column
and states the cells — both reference the substrate, never re-declare
it.

[[time-primitives]]
=== Time primitives

The time value types are texts in ISO 8601 formats, validated with real
calendar arithmetic (C35):

* `date`: a calendar date, `2026-08-20`, with leap-year validation;
* `datetime`: a date with a time of day, `2026-09-15T10:14:00Z`, with an
optional UTC offset;
* `duration`: a duration designator, `P2Y`, `PT1H30M`, with the
designators in order and optional decimal fractions;
* `period`: a recurrence period, validated as a duration.

[[tables-symbols-calculations]]
=== Tables, symbols, and calculations

The table/class doctrine: **`table`** carries a closed key→value
register consulted by rules — typed columns, data rows, profiles;
**`class` + `instance`** carries subject-bound data with provenance and
edition pins. The choice is a stated rule, not a taste: rule-consulted
registers are tables; subject-bound, edition-pinned facts are classes
and instances.

A `table` declares structured tabular data: typed `columns { ... }` with
optional units, `data { ... }` rows (numeric-looking cells coerce to
numbers), `profiles { ... }` (named row selections), `dimension` binding,
`overrides`, and `binding`. A `symbol` declares a typed, unit-aware formal
symbol: `type` is a closed vocabulary, parse-enforced (`number`,
`integer`, `string`, `boolean`, `enum`, `collection`, `array`), with
`unit`, `values`, `series`, `kind`, `quantity_kind`, `origin`,
and the linking facets `attribute`, `calculation`, and `profile`.
The `latex` facet is RETIRED: a per-symbol glyph is derived
presentation the math engine renders, never model semantics.

A `calculation` declares a named computation: `inputs { ... }`,
`output { ... }`, and one of the calculation forms, `math`
(declared math in a declared notation, <<calculation-math,13.x>> —
the form all new calculations use), `expression` (the retired OCL
surface, read-only for the migration window), `lookup` (a table
lookup with `key`), or `profile` (a profile reference), with
`params { param <name>: <type> { ... } }`, `variable` bindings, and
provenance.

[[calculation-signatures]]
==== The calculation signature: typed inputs and outputs

A retrieved calculation
is executable exactly when its signature is data: what goes in, in which
units, over which ranges, and what comes out. The signature declares it:

[source,prl]
----
calculation mpe_absolute {
  inputs {
    e_l : number { unit kg quantity_kind mass range { min 0 }
      description "Error of indication at the test load." }
    n_lc : integer { range { min 1 max 10000 }
      description "Number of load cell intervals." }
  }
  output : number { unit kg quantity_kind mass range { min 0 }
    name "mpe" description "Maximum permissible error, absolute." }
  expression "ocl{...}"
  ref derives-from "urn:oiml:pub:r:60-1:2021#clause-5.1"
}
----

An input entry keeps the v2 `<name> : <type> { ... }` form; the block
carries `unit` and `quantity_kind` (the typed-unit pair, resolved
against the merged quantity register of <<quantities,13.4>>), `range
{ min max }` (the admissible domain; either bound may be absent),
`description`, `default`, and `enum_values` for enum-typed inputs. The
`output : <type> { ... }` carries the same typing facets with `name` and
`description`. The checker verifies the signature (C115,
`calculation-signature-shape`): every `unit` resolves to a registered
unit and every `quantity_kind` to a registered kind of the merged
quantity register (unit resolution is reported as a warning by the
reference toolchain during the v3.2 rollout — the estate declares units
no register carries yet; the leg tightens to an error when the registers
catch up, TODO.primmel/11d), the two agree in kind, a range's `min`
never exceeds
its `max`, and an enum-typed input declares its values. Unit-aware
retrieval ("limits expressed in mV/V") and the trustworthy execution of
a retrieved calculation both read this signature; they never parse the
expression text for units.

[[uncertainty-budget]]
=== The uncertainty budget

An `uncertainty_budget` declares one measured quantity's uncertainty
components and the coverage factor of the expansion — the language side
of the GUM plane. The budget is a DECLARATION: the propagation law is
the GUM's, computed by the evaluation plane; the model names the
components, their kinds, and their provenance, never the arithmetic.

[source,prl]
----
uncertainty_budget u_ref {
  target mpe_error
  coverage k 2
  component u_cal {
    type B
    distribution rectangular
    half_width 0.5
    unit "kg"
    ref derives-from "urn:example:cert:2026#clause-5.1"
    description "The force standard's certificate half-width."
  }
  component u_rep {
    type A
    series reference_pair_error
  }
}
----

The facets: `target` names the verdict whose quantity the budget
expands; `coverage k` states the coverage factor of the expansion; each
`component` carries an id and its kind — `type A` evaluates the
statistics of a captured `series` (a conformance test's declared series
variable), `type B` states a `distribution` (`rectangular`,
`triangular`, `normal`, `ushape` — a closed vocabulary, parse-enforced)
with its `half_width` and `unit`. Components and the budget itself take
`source` provenance and `description`. One component per uncertainty
contribution; Type A and Type B components mix freely in one budget.

The checker resolves the budget's references (C179,
`uncertainty-budget-resolves`): the target names a declared verdict,
every Type A series names a captured series variable, and every Type B
component states both its distribution and its half-width.

[[test-point-sets]]
=== Test point sets and reference materials

A `test_point_set` declares the points at which a test samples its range:
`anchor`, `points` (or `min_points`), `fraction`, `offset`,
`repetitions_per_point`, `rule`, `cardinality`, and provenance. A
`reference_material` declares a certified material used by a test:
`identity_fields`, `constraints`, `evidence`, `override`, `kind`, `type`,
`unit`, and `required` facets, with the parse-enforced gate facets
(`on_violation`, `rule`) where the grammar defines them.

[[registry-assurance]]
=== Registry and assurance constructs

Four documentation constructs round out the registry: `note` (a typed
annotation; `type` is a closed vocabulary, parse-enforced: `NOTE`,
`CAUTION`, `WARNING`, `EXAMPLE`, `COMMENTARY`; facets `message`,
`reference`, and `source_discrepancy`), `link` (a cross-model or external
pointer; `kind` is `REPO` or `URL`, parse-enforced, with `target`, `url`,
`path`, `namespace`), `figure` (`src`, `title`), and `comment` (a review
comment: `author`, `message`, `on`, `reply_to`, `resolved`, `timestamp`).

Three assurance constructs carry the architecture-level records: an
`invariant` declares a named platform invariant with `statement`,
`severity`, `applies_to { ... }`, and `enforcement` (a claims list, or the
bare marker `aspirational`; the grammar and the marker discipline are
checker-enforced, C90, C91). A `test_sequence` declares a required test
ordering: step entries `step <n> { test <ref> role <r> depends_on <m> }`
with the step role (`baseline` or `follow_up`), `sample_applicability`,
and provenance (shape and integrity: C92, C93).

[[terminology-construct]]
=== Terminology

A `term` declares one entry of the model's terminology register:

[source,prl]
----
term load-cell {
  label "load cell"
  definition { Force transducer that converts a load into an electrical signal. }
  symbol "LC"
  part_of_speech noun
  aliases { "weighing cell" }
  abbreviations { "LC" }
  see_also { force-transducer }
  scope_note "Used for the R 60 sense only."
  ref derives-from "urn:oiml:pub:r:60-1:2021#clause-3.1.3"
}
----

The facets are `label`, `definition`, `symbol` (the formal symbol of the
term), `part_of_speech`, the alias family (`aliases`, `colloquial`,
`abbreviations`, `deprecated`; <<term-alias-family,13.10.1>>),
`form_type`, `language`, `note`, `scope_note`, `section`,
`see_also { ... }`, `vocab_ref` / `vocab_term` (the external vocabulary
binding), `overlay` (a term-level overlay marker), and provenance. Terms
are foundations-tier content: every tier references them and they anchor
to no subject.

[[term-alias-family]]
==== The alias family

The designation set of a term is
data, and it is the bridge a consumption system (a search index, a
retrieval plane, an assistant) walks from the vocabulary a user actually
types to the defined term the corpus knows. Four facets carry it, each
a list of strings (multiword entries quote, per the lexical rules of
<<tokens,8.3>>):

[cols="1,3"]
|===
|Facet |Meaning

|`aliases { ... }`
|Admitted alternate designations of the same concept: forms the
standard's community accepts as naming the term (`alt` is the v2
spelling of this facet; it parses unchanged and folds into the same
channel, and a conforming serializer emits the canonical `aliases`
form).

|`abbreviations { ... }`
|Abbreviated forms of the designation.

|`colloquial { ... }`
|Informal, everyday phrasings users reach for when they do not know the
defined term: "why is my scale drifting" belongs on the `durability`
term. Colloquial entries are NOT designations: they carry no normative
force and a renderer never presents them as the term's name. They exist
so the everyday-words → defined-term bridge is authored once, in the
model, instead of being hand-rolled per consumer.

|`deprecated { ... }`
|Deprecated designations: recognized, never proposed.
|===

[source,prl]
----
term durability {
  label "durability"
  definition { Ability of a measuring instrument to maintain its performance characteristics over a period of use. }
  aliases { "long-term stability" }
  colloquial { "drifting" "scale keeps drifting" "readings creep over months" }
  colloquial fra-Latn { "dérive" "les lectures dérivent" }
  see_also { stability }
  ref derives-from "urn:oiml:pub:r:60-1:2021#clause-3.1"
  vocab_ref viml-2022
  vocab_term "5.15"
}
----

An alias-family facet may carry a spelling code between the keyword and
the list (`colloquial fra-Latn { ... }`), declaring the list of one
alternate spelling inline; the bare form declares the package's default
spelling (<<multilinguality,clause 15>>). The spelling-tagged form is
the language-level construct for language-tagged designation variants:
the designation set of one spelling is one list, so a retrieval consumer
routes a question to the entries authored in its language. The `text`
block mechanism does not address alias-family lists item by item (a bare
string entry has no declared key to key on); the inline tagged form is
the whole of the variant mechanism. The serialization of the variant
lists (per-unit language tags in a retrieval export) is the toolchain's
projection (primmel-ts#65, ask 7).

The checker verifies the family's shape (C110, `term-alias-shape`):
duplicate entries within one list of one term are errors, and the same
string appearing in two different family fields of one term violates
one-entry-one-home (reported as a warning by the reference toolchain
during the v3.2 rollout — the v2 `alt` semantics admitted the overlap
and the shipped estate carries it; the leg tightens to an error when the
estate's terms are re-authored, TODO.primmel/11d); an entry that merely
echoes the term's `label` is a warning (it adds no bridge).

[[twin-era-constructs]]
=== Twin-era constructs

Three constructs serve a live subject: a `connector_profile` declares a
named protocol profile that endpoints reference (facets `protocol`,
`description`, `reference`); a `monitor` declares continuous
compliance over a subject set, with `over { ... }`, `triggers { ... }`
(`every <period>`, `on signal <s>`, `on change <aspect>`), `evaluate`
selectors (`all`, `applicable_to(<expr>)`, or an explicit id block),
`emit` sinks, and `escalate { ... }` actions on fail and on invalid
(checker rules C65–C70); a `passport` declares a named, access-classed
projection of a product model, with `upi { pattern level }` (the level is
`model`, `batch`, or `item`, C88), `carrier { kind payload }`, and the
access-class content blocks (`public`, `restricted`, `authority`), which
are fail-closed at parse: an unknown block-valued keyword is a parse
error, so a misspelt access class never parses into content no class
serves (C86, C87).

[[calculation-math]]
==== The calculation math: declared notation, declared symbols

Math is NOT in OCL. A calculation's formula is DECLARED MATH, in a
declared notation, bound to declared symbols. The `expression "ocl{…}"`
form is retired for calculations (checks keep OCL — boolean logic is
logic, not math):

[source,prl]
----
symbol load_v {
  type number
  quantity_kind si:dimensionless
  unit si:1
  render latex "L_{v}"
  render asciimath "L_v"
}

symbol mpe {
  type number
  quantity_kind si:dimensionless
  unit si:1
  render latex "mathrm{MPE}"
}

calculation mpe_tiers {
  math {
    notation asciimath
    formula "p_LC * factor(load_v)"
  }
  inputs {
    load_v : number { unit si:1 }
    p_lc : number { unit si:1 }
  }
  output : number { unit si:1 symbol mpe }
  ref derives-from "urn:oiml:pub:r:60-1:2021#clause-5.3.2"
}
----

Rules:

. the `math` block carries `notation` — one of `asciimath`, `latex`,
`unicodemath`, `mathml`, `omml` (parse-enforced) — and `formula`
(a quoted string; for the XML notations, a block payload). The formula
MUST parse in its declared notation under a Plurimath-conformant
engine; the reference engine is plurimath-ts (C166).
. every identifier appearing in the formula is a DECLARED symbol bound
to the calculation — an input, the output, or a declared constant
(C165). The formula's symbols resolve by name; an undeclared
identifier in math is a checker error, never a silent variable.
. inputs and output bind the symbol registry: a signature entry's
`symbol` facet names a declared `symbol` construct (which carries the
`latex` glyph, `quantity_kind`, `unit`); the entry's own typing facets
must agree with the symbol's (C115). One output, exactly one; inputs
one or more.
. the OUTPUT SYMBOL is the result's address: downstream calculations
bind it as an input, steps bind it through the binding edge
(<<steps-and-flow,12.2>>), forms bind it into fields, evidence records
carry it. Results are read out, reused, and linked BY SYMBOL — the
symbol is the link.
. units and quantity kinds reference AUTHORITATIVE registries only:
`unit unitsdb:degC`, `quantity_kind si:mass` — the namespace prefix is
a CLOSED, parse-enforced vocabulary: `si` (the digital SI framework /
D-SI) and `unitsdb` (NIST UnitsDB). No package invents a unit
namespace; a quantity the registries do not carry is expressed as a
combination of the units they do (a ratio of masses carries
`quantity_kind si:dimensionless, unit si:1`), and a genuinely novel
unit is contributed to the authoritative registry, never declared
locally (C167). The package-level quantity register no longer DECLARES
units; it carries the usage set and the correspondences
(<<correspondence-annotations,19.4>>).
. rendering HINTS are declared, per notation, with the notation NAMED:
`render latex "L_{v}"`, `render asciimath "L_v"` — zero or more per
symbol, the notation parse-enforced. The hint is presentation data
(it names its notation, so it is useable), consumed by the math engine
when it renders the formula in that notation; absent hints fall to the
engine's default rendering of the identifier. The retired bare
`latex` facet carried no notation and no form — that is why it was a
