[[requirements-and-conformance]]
== Requirements and conformance

[[requirement-construct]]
=== Requirement classes and requirements

A `requirement_class` groups the requirements of one domain area; its
identifier convention is a path (`/req/metrological`), and its facets are
`name`, `subject`, `guidance`, and provenance.

A `requirement` is a constraint over the aspect paths of a subject:

[source,prl]
----
requirement /req/metrological/mpe {
  name "Maximum permissible error"
  statement "The error of indication shall not exceed the mpe."
  guidance "..."
  binds_to { model.parameters.mpe model.classification.accuracy_class }
  subjects {
    subject 1 { entity_id "dimensions.p_LC" label "Apportioning factor" }
  }
  parameters {
    param n_runs: integer { description "..." default 20 range { min 0 max 100 } }
  }
  limit {
    args {
      mpe   <- symbol:mpe
      p_lc  <- symbol:p_lc
    }
    expression {
      abs(p_lc * n_runs) <= mpe
    }
    modality should
    relative_to reference_speed
    notes "..."
    accepts { verdict mdlo_normalized op lte limit "ocl{p_lc}" }
    acceptance { rule guarded guard_band { kind NSFa value 0.5 } }
  }
  applicability { accuracy_class: [A, B, C, D] }
  channel measurand_components
  obligation should
  acceptance_criteria { threshold { operator "<=" value "ocl{...}" } }
  verification { method testing }
  dependencies { /req/other }
  ref derives-from "urn:oiml:pub:r:60-1:2021#clause-5.3.2"
}
----

The principal facets:

[cols="1,3"]
|===
|Facet |Meaning

|`statement`
|The normative sentence (the text the committee owns).

|`binds_to { ... }`
|The aspect paths the requirement constrains. The anchoring rule
(<<tier-system,7.2>>): a requirement binds subject facts, it never
restates them.

|`subjects { subject <n> { ... } }`
|The per-subject apportioning of the constraint.

|`parameters { param <name>: <type> { ... } }`
|Typed parameters — the requirement's instance-parameter schema:
`description`, `unit`, `default`, `range { min max }`, `enum_values`,
and `bind` (the aspect path the parameter instantiates from;
<<instance-parameters,11.1.3>>).

|`limit { ... }`
|The formal limit: `expression` (a quoted OCL payload,
<<embedded-expressions,8.6>>, or the inline block,
<<limit-expressions,11.1.4>>), `args` (the inline body's scope,
<<limit-expressions,11.1.4>>), `uses` (the legacy form's free
variables), `modality`, `relative_to`, `notes`, `quantity { kind unit }`
(the derived quantity's typing; <<limit-quantities,11.1.2>>), `accepts`
(the verdict binding: `verdict`, `op`, `limit`, an optional
`source_discrepancy`), and `acceptance` (<<acceptance-decisions,11.5>>).

|`applicability { ... }`
|Dimension-keyed applicability entries; a value is a bare id, a quoted
text, a bracket list (<<bracket-lists,8.7>>), or a parameter-mapping
block. A `match` mode of `any`, `all`, or `exact` is a closed
vocabulary, parse-enforced. The dimension namespace and the entry
semantics: <<applicability-semantics,11.1.1>>.

|`channel`, `obligation`
|The evidence channel and the obligation level
(<<modality-vocabulary,11.6>>).

|`acceptance_criteria { ... }`
|The threshold form of the decision rule.

|`verification { method ... }`
|The verification method of the requirement.

|`dependencies { ... }`
|Other requirements this one depends on.

|`source_discrepancy { ... }`
|The named-difference record against the source text
(<<discrepancy-records,14.5>>).
|===

[[applicability-semantics]]
==== The applicability entry: namespace and match semantics

An `applicability { ... }` block appears on requirements, requirement
classes, conformance classes, conformance tests, forms, and subform
references — one grammar everywhere. Each entry is
`<dimension> : <value> [ match <mode> ]`, and the dimension is TYPED:
the key resolves into the *applicability dimension namespace* of the
merged package — the union of the instruments' classification dimensions
(<<five-entity-kinds,10.1>>), the attribute definitions declared
`is_dimension true`, and the top-level dimension declarations
(<<dimension-construct,10.6>>) — and each listed value resolves against
the dimension's declared value set or its `implies` subsumption closure
(the applicability engine walks the closure, so a subject holding
`ac-and-battery` matches an entry listing `battery`). Both resolutions
are checker-enforced (C3): an applicability entry keyed on an undeclared
axis, or naming a value outside the axis's domain, is an error, not a
silent string.

The value forms:

* a bare id or quoted text: one value of the dimension;
* a bracket list `[A, B, C]`: the value set;
* a mapping block `{ A: 5, C: 3 }`: applicability PLUS per-value
parameter resolution — the entry applies where the dimension holds a
listed value, and the map carries that value's parameter assignments
(the per-classification parameterization the `instances` facet of a test
states explicitly, <<conformance-test-construct,11.2>>).

The `match` mode refines matching on set-cardinality dimensions: `any`
(the default; existential — one selected value listed suffices), `all`
(universal — every selected value must be listed), and `exact` (mutual
coverage — the selection equals the listed set, without implies
expansion). On a single-cardinality dimension the selection holds at
most one value, so `all` and `exact` reduce to `any`; the checker warns
(C3) so the author either sets the dimension's cardinality or drops the
mode.

[[limit-quantities]]
==== The limit's quantity typing

A machine limit is a quantity, and
its typing is data: `quantity { kind unit }` on the `limit` block
declares the derived quantity's kind and unit — the same contract the
`verdict` construct carries (<<verdict-construct,11.3>>) and the
calculation signature declares (<<calculation-signatures,13.7.1>>).
When the limit binds a verdict (`accepts`), the two declarations must
agree: the checker verifies that the limit's `kind` and `unit` match the
verdict's declared quantity (C114, `limit-quantity-coherence`), so a
limit and its acceptance chain can never drift apart in units. A limit
with no quantity block remains conforming — the facet is the migration
path, and a quantitative limit SHOULD declare it: the block is what
makes "limits expressed in mV/V" a unit lookup instead of a string
search, and what lets an execution environment normalize the compared
quantities (quantity-kind coherence, never string matching,
<<quantities,13.4>>).

[[instance-parameters]]
==== The instance-parameter schema

A requirement's `parameters { ... }` block is the
explicit schema for instantiating its check: which parameters a run of
the check takes, their types, their units and admissible ranges, and —
with `bind` — WHERE each value comes from:

[source,prl]
----
requirement /req/metrological/mpe {
  name "Maximum permissible error"
  statement "The error of indication shall not exceed the mpe."
  binds_to { model.parameters.mpe model.classification.accuracy_class }
  parameters {
    param n_runs: integer {
      description "Repetitions per test point."
      default 20
      range { min 1 max 100 }
    }
    param e_max: number {
      description "Maximum capacity of the instrument under test."
      unit kg
      bind "model.parameters.e_max"
      range { min 0 }
    }
  }
  limit {
    args {
      mpe    <- symbol:mpe
      e_max  <- attribute:e_max
    }
    expression {
      abs(served - nominal) <= mpe
    }
    quantity { kind mass unit kg }
    accepts { verdict mpe_error op lte limit "ocl{...}" }
  }
  applicability { accuracy_class: [A, B, C, D] }
  ref derives-from "urn:oiml:pub:r:60-1:2021#clause-5.3.2"
}
----

A `bind` names the aspect path that supplies the parameter's value —
into the subject's IS catalog (`model.parameters.e_max`), its
classification (`dimensions.accuracy_class`), or the run context — the
same path discipline as the form field's `bind`
(<<form-constructs,11.8>>) and the requirement's own `binds_to`. The
instantiation order is fixed and deterministic:

. a `bind` path resolves against the instance under test (its exhibited
values, <<instance-construct,10.3>>);
. a parameter with no `bind` falls back to its `default`;
. a parameter with neither is caller-supplied — derivable from the
schema alone, so an execution-side system knows exactly which inputs to
ask for.

This is the binding contract an execution environment (the primmel/sst
runtime is the estate's) needs to bind a user's instrument instance to
the model deterministically — "for THIS instrument instance, does it
pass?" becomes a deterministic read, never a guess: the schema says
which parameters instantiate the check, `bind` says their provenance,
`unit`/`range` say their domain. The checker verifies the schema (C118,
`requirement-parameter-shape`): a `bind` path resolves against the
subject's aspect catalog, a `unit` resolves against the merged quantity
register (reported as a warning by the reference toolchain during the
v3.2 rollout — the estate declares units no register carries yet; the
leg tightens to an error when the registers catch up,
TODO.primmel/11d), and a range's `min` never exceeds its `max`.

[[limit-expressions]]
==== The limit: the expression body and its arguments

The limit's machine-executable predicate has two carriers. The *legacy*
carrier is a quoted OCL payload, `expression "ocl{...}"`, whose free
variables ride the `uses { ... }` list. The *inline* carrier (v3.3) is a
delimited block, `expression { ... }`: the raw formula, never quoted,
parsed at load. The legacy string and the inline block never mix in one
limit — the value's shape (a string or a block) is the entire decision.

The inline limit is a *function*: it takes declarative arguments, and the
scope is passed into it. An `args { ... }` block binds each local name to
its declaration — one binding per line, `name <- source`:

[source,prl]
----
limit {
  args {
    e_vehicle  <- symbol:e_vehicle
    mpe_class  <- table:vehicle_mpe.mpe_initial
    d          <- attribute:scale_interval
    n_axles    <- observable:n_axles
  }
  expression {
    abs(e_vehicle) <= max(mpe_class, 1 * d * n_axles)
  }
  notes "Table 2 percentage of the conventional value (6.7)."
}
----

The block order is canonical: `args`, the expression, then the
documentation and acceptance facets (`modality`, `relative_to`, `notes`,
`quantity`, `accepts`, `acceptance`, `source_discrepancy`).

The binding sources:

[cols="1,3"]
|===
|Form |Binds to

|`symbol:<id>`, `table:<id>`, `datum:<id>`, `verdict:<id>`, `attribute:<id>`
|A declaration of this package's own registries. A dotted id rides the
declared object (`table:vehicle_mpe.mpe_initial` names a column of the
declared table).

|`observable:<id>`
|The dispatch context — the readings the run observes.

|`self.<path>`
|The subject aspect the requirement constrains.

|`process:<p>.<step>[.<io>]`
|The step plane (register 19): a declared process, one of its steps,
or one of the step's declared signature inputs or outputs. The dot
descends the declared structure; the leaf names a declared io (C173,
`step-plane-refs-resolve`, checks the descent).

|`<package>:<kind>:<id>`
|A declaration across a `uses` edge; the composed closure resolves it.
|===

The *resolution doctrine*: the body's identifiers are the args and
nothing else — an identifier naming no argument is air inside the
formula and is rejected (C171, `expression-identifiers-resolve`). Three
exceptions are context, never ambient scope: a path rooted at `self`; a
path rooted at one of the dispatch-context roots (`sample`, `family`,
`group`, `model`, `instrument`, `specimen`) — the pronouns of the
dispatch, allowed as path roots, never as bare scalars; and the closed
function vocabulary — `abs`, `max`, `min`, `floor`, `ceil`, `round`,
`sqrt`, `exp`, `ln`, `log`, `mod`, `sum`, `count`, `exists`, `forall`.
A call whose target is a dotted path (`table.permits(a, b)`) or a bound
argument (a table lookup) rides its declared object — the root is the
check, the method is the object's own interface.

The expression grammar binds the usual precedence, loosest first:
`implies`, then `or`, `xor`, `and`, the comparisons (`<= >= < > = ≠`),
the additive operators, the multiplicative operators, unary `-` and
`not`, then the primaries — the bound names, the calls, the numeric
literals, the single-quoted string literals, and the parenthesised
groups. The collection navigation (register 24) rides the postfix
position: `collection -> forAll(v | body)`, `-> exists(v | body)`,
`-> select(v | body)` — the lambda parameter scopes the body exactly
like an argument binds the limit's, and the iteration predicate's
truth is the navigation's value. The serialized form is
canonical: the dumper re-emits the parsed tree's canonical source, and
the canonical source reparses to the same tree.

A `requirement_class`'s law (<<class-law>>) carries the
inline form with the args OPTIONAL: the class's containment is itself
the declared scope, and the law's identifiers are the members. An
explicit `args` block on the law adds bindings, each of which must name
a contained member (C172, `requirement-algebra-resolves`).

The inline carrier is the language's for every machine-executable
payload: the verdict's canonical derivation (`derive { … }`), the test
variable's derivation (`derivation { … }`), the run-validity check of a
precondition and the constraint's invariant (`check { … }`) — the same
string-vs-block carrier decision, the same canonical serialization, the
same AST-exact resolution (C171). A comparison inside an inline
expression sets operands of the same declared quantity kind (C177,
`kind-coherence`): the kinds come from the args' declared sources, an
operand of unknown kind or a bare number never conflicts, and the unit
algebra stays with the evaluation plane — the checker names the kinds,
it does not compute them.

[[conformance-test-construct]]
=== Conformance classes and conformance tests

A `conformance_class` scopes a family of tests to a requirement class:

[source,prl]
----
conformance_class /conf/metrological-tests {
  title "Metrological tests"
  target /req/metrological
  subject "LoadCell"
  applicability { accuracy_class: [A, B, C, D] }
  guidance "..."
}
----

A `conformance_test` is an operation on the subject:

[source,prl]
----
conformance_test /conf/metrological-tests/mpe-test {
  type Testing
  targets { /req/metrological/mpe }
  test_subject { kind model }
  variables {
    variable applied_load { type mass unit kg source measured
      provenance { channel reference_instrument ref eq-013 observed_at t_log } }
    variable e_l { type mass unit kg source derived
      derivation {
        indication - applied_load
      } }
  }
  observables { observable indication_series { quantity_kind mass unit kg } }
  preconditions {
    precondition warmed-up {
      check {
        self.state = #ready
      }
      description "An unwarmed run is invalid, never a fail."
      on_violation invalid
    }
  }
  design {
    selection { ... }
    test_points { count 5 }
  }
  instances {
    by accuracy_class
    values { A { n_runs: 5 } C { n_runs: 3 } }
  }
  acceptance_criteria { criterion mpe-check { expression "ocl{...}" } }
  pass_if "ocl{...}"
  acceptance { rule guarded guard_band { kind NSFa value 0.5 } }
  result_forms { mpe-report }
  produces_artifacts { evidence-file }
}
----

The principal facet groups: `type` (the test kind), `targets` (the
requirements under test), `test_subject`, `variables` (typed test
variables; the `source` vocabulary is `declared`, `measured`, `derived`,
`computed`, `lookup`, and a measured reference variable carries a
`provenance` probe channel, <<probe-channels,11.4>>), `observables`,
`preconditions` (a gate with `check`, `description`, and `on_violation`),
`design` (the test design: selection rules, counts, phases, specimens,
test points, and the validation facets), `instances` (per-classification
parameter values), `acceptance_criteria` and `pass_if` (the decision),
`acceptance` (<<acceptance-decisions,11.5>>), and the output anchors
(`result_forms`, `produces_artifacts`, `report_rows`,
`reference_materials`, `required_competence`). `inherits_from` reuses
another test's definition; `dependencies` orders.

[[verdict-construct]]
=== Verdicts

A `verdict` is a named, reusable derivation of a judged quantity: derive
once, reference everywhere.

[source,prl]
----
verdict drift_error {
  quantity { kind volume-fraction unit "ppm" }
  derive {
    indication - cgm_certified_value
  }
  inputs { indication cgm_certified_value }
  series_reduction max_abs_over_window
  ref derives-from "urn:oiml:pub:r:144-2:2013#clause-4.8"
}
----

The facets are `symbol`, `behavior` (the behavior the quantity derives
from), `quantity { kind unit }`, `derive` (the expression), `inputs`,
`series_reduction` (a closed vocabulary, parse-enforced: `none`, `max`,
`mean`, `worst_case`, `max_abs_over_window`), `acceptance`
(<<acceptance-decisions,11.5>>), and provenance. Requirement limits,
conformance tests, and form fields reference the verdict identifier
instead of restating the derivation.

A verdict's `inputs` name the free identifiers of its derivation, and an
input may name another VERDICT: the
acceptance chain is then an explicit graph, not an implicit one —
requirement → `limit.accepts.verdict` → the verdict's `inputs` (symbols
and sub-verdicts) → each verdict's `acceptance` — and every hop is a
declared, citable model element with its own identifier and clause
provenance. The checker keeps the graph honest (C116,
`verdict-inputs-resolve`: every input resolves to a declared symbol, a
test variable or observable, or another verdict; C117,
`verdict-chain-acyclic`: the verdict graph never cycles). A consumption
system can therefore cite "the acceptance chain" precisely — the
decision structure is retrievable data — and traverse it: from a
verdict to the quantities it derives from, the tests that produce them,
and the requirements that bind it.

[[probe-channels]]
=== Probe channels

A measured test variable may declare the physical channel its reference
reading arrives by. The channel vocabulary is closed and checker-enforced
(C99): `reference_instrument` (a traceable reference, cited by equipment
register id), `observer_attestation` (a verification officer reads the
physical display into the evidence form), and `sim_ground_truth` (the
acceptance environment only, never a production channel). An
`observer_attestation` channel MUST carry its declared traceability
`limitation` text (C99).

[[acceptance-decisions]]
=== Acceptance decisions

An `acceptance { ... }` block states how a limit comparison decides
conformity. It attaches to requirement limits, conformance tests, and
verdicts. Its vocabularies are closed and parse-enforced:

* `rule`: `shared_risk` or `guarded`;
* `guard_band { kind value }`: kind is `NSFa`, `NSFd`, `absolute`, or
`ratio`;
* `criterion`: `I/MPE`, `D/NSFa`, `D/NSFd`, or `n/a`;
* `uncertainty { max_ratio_to_mpe ... }` and
`statistics { method on_basis_of permits }` carry the uncertainty and
sampling facets.

[[modality-vocabulary]]
=== The modality vocabulary

Modality facets carry the RFC 2119 vocabulary, extended with `CAN`:
`SHALL`, `SHOULD`, `MAY`, `CAN`, `MUST`. These tokens are *model content*:
they state the obligation of a provision, process, field, or approval of
the modelled standard, and they are not conformance keywords of this
specification (<<normative-keywords,6.1>>). The `obligation` facet of
requirements and tests carries the same vocabulary in lower case
(`shall`, `should`, `may`) as data; the value is stored as text and
program linkers check it.

[[uncertainty-budget]]
=== The uncertainty budget

An `uncertainty_budget` declares the GUM components of one measured
quantity's standard uncertainty and the coverage factor of its
expansion. The budget is a DECLARATION — the propagation law
(u_c = √(Σ uᵢ²), U = k·u_c) is the GUM's, computed by the evaluation
plane; the model names the components, their kinds, and their
provenance, never the arithmetic:

[source,prl]
----
uncertainty_budget u_creep_reference {
  target twin_creep_drift_indication
  coverage k 2
  component u_std {
    type B
    distribution rectangular
    half_width 0.25
    unit "kg"
    source { doc "urn:oiml:pub:cs:twin-1:2027" clause "6" }
    description "The force standard's certificate half-width."
  }
  component u_pair {
    type A
    series reference_pair_error
  }
}
----

The facets are `target` (the declared verdict whose measured quantity
the budget backs), `coverage k` (the expansion factor; the GUM's
default 2 applies when omitted), and the `component` entries. A Type A
component evaluates the statistics of a captured series — its `series`
names a declared test variable carrying the series shape. A Type B
component states a `distribution` (rectangular, triangular, normal,
ushape — the GUM's input models; the divisor rule is the evaluation
plane's) around its `half_width`. The checker verifies the resolution:
the target is a declared verdict, a Type A series is a declared
captured series, a Type B component states its distribution and
half-width, and the coverage factor is a positive number
(<<checker-catalog,C179>>).

[[constraint-construct]]
=== Constraints

A `constraint` declares a subject-intrinsic rule (an invariant of the
subject, distinct from a requirement, which is an external obligation):

[source,prl]
----
constraint e-max-bound {
  name "Applied load within capacity"
  stereotype inv
  check {
    self.applied_load <= self.e_max
  }
  on_violation invalid
  violation_meaning "A run above capacity is not a test result."
  source { doc "urn:oiml:pub:r:60-2:2021" clause "2.3" }
}
----

The facets are `name`, `stereotype` (the constraint kind; `inv` is the
intrinsic-rule stereotype), `check` (the embedded expression),
`on_violation`, `violation_meaning`, and provenance. The constraint shape
is checker-enforced (C84).

[[form-constructs]]
=== Forms and subforms

A `form` is the evidence view of the secondary tier: a declarative
data-capture schema that projects the subject graph into a record.

[source,prl]
----
form mpe-report {
  name "MPE test report"
  data_class MpeReport#data
  conformance_process creep_test
  section "E"
  field e_max: number {
    label "Maximum capacity"
    bind "model.parameters.e_max"
    unit kg
    required true
  }
  field runs {
    label "Runs"
    subform_ref run_row { parameters { n: n_runs } }
    min_items 3
  }
  pass_if "ocl{...}"
  calculation_context { mpe_eval }
  applicability { accuracy_class: [A, B, C, D] }
}
----

The principal facets: `name`, `data_class` (the record the form fills),
`conformance_process`, `header` (a shared header form), `section`,
`scope`, `dimensions`, `requirements { ... }` (the requirements the form
serves), `references`, `applicability`, `instances`, `constraints`,
`criteria`, `tables`, `calculation_context { ... }` (the calculations in
scope), `pass_if` / `pass_fail` / `derivation` (the form-level judgment
derivations), and `report_rows { ... }`. A
`field <name>[: <type>] { ... }` entry carries `label`, `definition`,
`bind` (the aspect path the field records), `unit`, `symbol`, `verdict`
(the verdict the field derives, <<verdict-construct,11.3>>), `targets`,
`dimension`, `enum`, `pattern`, `required` or `required_when` (a
conditional-requiredness expression), `default`, `values` /
`enum_values`, `evaluation`, `calculation_bindings`,
`measurement_method`, `items` / `fields` (nested structure), `min_items` /
`max_items`, `subform_ref`, and provenance.

A `subform` declares a reusable parameterized row shape:
`parameters { ... }`, `type`, `default`, `mapping`, and the same `field`
entries. The field grammar of forms and subforms is one grammar, shared.

[[provision-construct]]
=== Provisions

The `provision` is the v2 compliance primitive, retained: a statement of
requirement with RFC 2119 modality, traceable to source clauses.

[source,prl]
----
provision MoistureRecorded {
  condition "Every roast batch shall have its moisture content recorded"
  modality SHALL
  reference {
    BFS-4-2
  }
}
----

The facets are `condition` (the requirement text), `modality`
(<<modality-vocabulary,11.6>>), and `reference { ... }` (the cited
reference constructs, <<provenance-forms,14.3>>). Processes bind
provisions with `validate_provision { ... }`
(<<process-subject,12.1>>). In a v3 model the `requirement` construct
(<<requirement-construct,11.1>>) is the binding form: a provision states
text and modality, while a requirement additionally binds subject aspect
paths, carries a formal limit, and joins the coverage calculus. New
modelling SHOULD author requirements; provisions remain for the v2
surface and for standards whose provisions bind nothing.

[[check-primitive]]
=== The check primitive

"Evaluate an expression and compare" is ONE construct. The surface
spellings — a requirement's `limit { expression { ... } }`, an
acceptance_criteria triple (type/operator/threshold), a process's
`validate_measurement "…"` string, a form's `pass_fail { pass_if … }`,
and the `constraint` construct — are consolidated surface forms over
the one `check`:

[source,prl]
----
check within_mpe_check {
  inputs { errors : number { unit v } mpe : number { unit v } }
  expression {
    errors -> forAll(e | e <= mpe)
  }
  operator lte
  threshold { symbol mpe }
  ref derives-from "urn:oiml:pub:r:60-1:2021#clause-5.3.2"
}
----

Rules:

. a check declares named inputs (C160: signature coverage — every
consumed name is produced by a binding source), a boolean expression
in the OCL dialect (logic, not math — calculations are declared math,
<<calculation-math,13.x>>), and optionally an operator + threshold
pair (the acceptance-criteria sugar);
. every identifier in the expression is a declared input, an output
of a bound step or calculation, or a declared symbol (C158, C165);
. the retired spellings parse unchanged and fold into the `checks`
collection; a conforming serializer emits the canonical `check` form;
. verdicts and acceptance decisions (<<verdicts,11.4>>,
<<acceptance-decisions,11.6>>) READ checks; they never re-evaluate
prose.

== Limits

Every requirement and requirement class carries its obligation as one or more
<<limits,limits>>. A limit is a function: it declares its **arguments** — each
bound to the qualified declaration it reads — and states an **assertion** over
those arguments. The scope is passed into the limit; nothing is ambient.

=== Argument bindings

[source.primmel]
----
requirement /req/metrological/mpe-vehicle-mass {
  limit {
    args {
      e_vehicle <- oiml-r134:symbol:e_vehicle
      mpe_class <- oiml-r134:table:two_axle_mpe.mpe
      d         <- oiml-r134:symbol:d
      n_axles   <- oiml-r134:symbol:n_axles
    }
    abs(e_vehicle) <= max(mpe_class, d * n_axles)
  }
}
----

A binding's source is **qualified by its kind**: `kind:id` names a
declaration of this package's own registries; `package:kind:id` — the
three-part scoped-reference grammar of the composition's capability
references, extended with the kind disambiguator and the optional
`.column` tail for tabular sources — crosses a `uses` edge, and the
composed closure resolves it. There is no ambient scope: an identifier
outside the args is air, whatever the binding's reach. The
member bindings of a class law (`member:<id>`) are the one special form —
the containment itself is the scope declaration. An identifier in the assertion that is
not a declared argument is a parse error: the formula is the executable core,
and nothing in it is air (<<checker-catalog,C171>>).

=== Multiple limits and applicability guards

A requirement carries a LIST of limits. Real standards bound different
sub-domains differently; each limit states the sub-domain it applies to as an
applicability guard over its own arguments:

[source.primmel]
----
requirement /req/metrological/mpe-ranges {
  limit "mpe-low-range" {
    args {
      e  <- oiml-r134:observable:e
      mu <- oiml-r134:table:vehicle_mpe.mpe_low
    }
    when {
      e <= 5000
    }
    abs(e) <= mu
  }
  limit "mpe-high-range" {
    args {
      e  <- oiml-r134:observable:e
      mu <- oiml-r134:table:vehicle_mpe.mpe_high
    }
    when {
      e > 5000
    }
    abs(e) <= mu
  }
}
----

Limits are named. The name is the limit's public handle: a conformance test
targets it, the coverage and the retrieval projection emit it
(`/req/metrological/mpe-ranges:limit/mpe-low-range`), the diff and the
edition mappings cite it, and the checker's diagnostics name the failing
limit. A name may be a quoted string (`"mpe-low-range"` — the natural
hyphenated form) or a bare identifier; the quoted form is unambiguous in
every context, and the split stays clean: the NAME carries the natural
wording, while the assertion's argument bindings carry the
expression-safe local names (`e`, `mu`) — a hyphen never has to survive
inside an expression. Multiple limits are a conjunction: every limit whose guard holds must
hold. A limit with no guard applies over the whole domain; a single unnamed
limit is accepted as the one-element shorthand. When the bound arguments
declare their domains, the checker verifies that the guards partition the
domain — no gap where no limit applies, no overlap where the assertion is
ambiguous.

[[class-law]]
=== The class law: containment is conjunction

A <<requirement-classes,requirement class>> contains its member
requirements; containment is conjunction — the class's obligation is its
members'. The class may state a **law**: a limit whose expression composes
the members with the logical connectives the source document states in prose
(and, or, either-or, neither-nor, unless):

[source.primmel]
----
requirement_class /req/electronic/software-protection {
  limit {
    expression {
      sealing or signalling
    }
  }
  requirement sealing { ... }
  requirement signalling { ... }
}
----

The containment is the law's scope: the law's identifiers are the
contained members, and the body takes the inline form
(<<limit-expressions>>). An explicit `args` block binds additional
names, each of which must name a contained member. A class with no law
is pure conjunction. The checker verifies the algebra: the law's identifiers name
contained members only, every member appears in the law or the class carries
no law, and a member's modality is never weaker than the class's
(<<checker-catalog,C172>>).
